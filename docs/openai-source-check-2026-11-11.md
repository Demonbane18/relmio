## Decision

The inspected changes improve local credential protection and recovery information. They do not establish permission for persistent VPS token storage or general-purpose use of a ChatGPT plan through other tools. Keep identity sign-in, granted plan permission and completed model requests separate.

Current text authentication is Relmio-owned SIWC Authorization Code + PKCE/OIDC. It is not the retired whole-Codex-credential-copy bridge. The optional image add-on still has its own Codex device grant and backend route; neither the SIWC Help Center article nor a working image login authorizes that separate integration.

## Check 1: identity sign-in

**Confirmed:** the Help Center article describes identity-provider sign-in, sharing name, email and optional picture. It expressly separates additional authorization and plan sharing from identity. Its statement that identity sign-in does not independently share tokens is not a description of every credential an authorized OSS application receives.

**Observed:** Relmio requests the combined identity/plan scope set, performs Authorization Code + S256 PKCE, validates one-use state, checks issued client identity, and verifies ID-token signature, issuer, audience, expiry, nonce and returning subject (`src/services/oauth.js:54-74,103-171,198-208`; `src/services/siwc-session.mjs:636-659`). Normalized identity stores issuer, subject and optional email; the retained ID token can contain additional claims (`src/services/siwc-session.mjs:545-601`). No reviewed text path imports personal `~/.codex/auth.json`.

**Finding:** the identity-only paragraph alone does not describe Relmio's full flow. Relmio implements the separately documented OSS plan-usage flow and receives access/refresh/ID tokens when granted. README/npm README correctly distinguish identity, plan permission and model access (`README.md:20-23,313-330`; `npm/README.md:17-27`). Do not rewrite this as an identity-only request or as a new migration away from Codex-copy authentication.

**Observed pre-existing difference:** current session guidance calls for retained `id_token_hint` during returning sign-in. Relmio retains the token but does not include that hint in its authorization parameters (`src/services/oauth.js:198-208`). Official guidance also describes the no-hint account-selector behavior. Record this as a protocol/UX difference, not evidence of missing identity verification or a new regression.

**Open:** actual account/workspace grant, current consent screen and successful login were not exercised.

## Check 2: separately approved permissions

**Confirmed:** inference requires granted `chatgpt.tokens.use.direct`, not merely requesting it or validating an ID token. Background use requires express consent. SIWC Terms §3.1 requires requests for the authenticated user's activity or expressly authorized automation, a runtime only that user controls, and use within the connected application. Another person's activity must not spend this user's plan. General-purpose API access for other tools or unrelated requests is prohibited.

**Observed:** Relmio derives granted scopes from the token response and combines the plan grant with local enablement and runtime ownership. Initial verified plan grants can enable text use; existing paused registrations stay paused. The wizard's first-use acknowledgment remains separate (`src/services/siwc-session.mjs:545-619,737-766`; `src/ui/siwc-controls.js:319-391`; `src/ui/index.html:256-259`). Acknowledgment is not itself provider consent. VPS install requires versioned background consent and final deployment confirmation (`src/services/installer.js:462-481`; `src/ui/index.html:887-905`).

**Observed:** local browser errors preserve `status`, `code`, `param`, `requestId`, recovery and uncertainty flags instead of losing them. The server still bounds/sanitizes returned failure data (`src/web/server.js:1550-1611`; `src/ui/siwc-controls.js:34-55`). Guide lookup prioritizes uncertain-operation flags over generic request advice (`src/ui/guide.js:47-63`). This supports the official recovery guidance; it adds no permission to retry an uncertain transfer or replace the account.

**Observed:** new network checks reject known unsuitable default bridge/host/none/internal networks at installation review (`src/services/discovery.js:163-190,217-245`; `src/domain/vps-network.js:17-29`; `src/services/installer.js:61-84`; `src/web/server.js:6378-6383`). Missing/unknown network fields can pass this particular classifier. A pass does not prove internet connectivity, OpenAI region eligibility, model admission or Terms compliance. The cached host report likewise makes no extra remote call and explicitly says it does not prove a later build (`src/web/server.js:3722-3739`; `src/ui/ssh-form.js:12,47-88`).

**Open: persistent remote storage.** SIWC Terms §1 still says persistent Authentication Tokens must be local and user-controlled, not in a remote or managed environment. The official VM guide expressly describes secure transfer to a self-hosted VM, and Terms §3.1 allows requests from a remote runtime only the user controls. These texts still leave the persistent-storage classification unresolved. Root-only permissions and final owner approval improve security but do not resolve the provider's wording.

**Open: connected application.** The sidecar accepts caller-selected messages, models and supported tools via OpenAI-compatible routes (`src/gateway/openai-oauth-sidecar.mjs:992-1080`). A local bearer or private Docker network does not establish application purpose or whose activity triggered the request. README/npm README already flag this issue for n8n (`README.md:163-169`; `npm/README.md:161-170`). Keep that warning. Identity success, successful inference and the documentation review are not blanket Terms compliance or permission to use a Codex credential bridge.

**Confirmed upcoming policy, applicability Open:** the fetched Usage Policies announce a November 20, 2026 requirement for prior review/approval of model-access intermediaries, with an exception for apps merely using models for their own features. It is future-effective on this check date. Record the date and reassess Relmio's connected-application classification before applying that future policy; do not claim it already bans all local OSS SIWC use or that Relmio has approval.

### Corrections made after this review

The boundary audit that followed found two defects in the reviewed worktree. Both were fixed the same day, and the statements above that describe the earlier behaviour are superseded by this section.
