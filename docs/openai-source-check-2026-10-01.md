# Frontend sign-in and credential-disclosure source check

Review date: 2026-10-01

This review covers the redesigned local wizard and dashboard, the hosted home and install pages, the hosted chat sign-in and request route, and their README, security, FAQ, and troubleshooting disclosures. It follows the [2026-09-29 check](openai-source-check-2026-09-29.md), but independently inspects the current application source and installed OAuth dependency code.

This is a read-only source review, not legal advice, release certification, or runtime acceptance. No files were changed, credentials accessed, sign-in completed, forms submitted, provider APIs called, or installs, builds, tests, SSH operations, or deployments run. Browser rendering and deployed Vercel bytes were not checked. References identify the worktree source inspected; concurrent edits can move line numbers. The comparison below uses the previous report as its historical baseline. A Git diff against `HEAD` was not available through this review's tools, so statements about changes mean changes from that report's recorded coverage and disclosures, not a independently verified commit-by-commit attribution.

Finding labels:

- **Confirmed:** supported by a fetched official OpenAI source.
- **Observed:** present in Relmio source or disclosure text; not a runtime claim.
- **Provisional:** based on installed third-party implementation or other non-OpenAI evidence; not provider approval or proof of deployed behavior.
- **Open:** the reviewed evidence does not resolve the question.

The main finding is that Relmio's hosted chat does **not** implement the currently documented OpenAI Sign in with ChatGPT identity or open-source plan-usage flow. It uses a third-party Codex-oriented OAuth flow, persists credentials in browser storage, and sends a reusable access token to a hosted server for inference through ChatGPT's `backend-api`. The newer official documentation supplies specific requirements against which this differs. Request-scoped server handling and encrypted browser storage are useful implementation facts, but neither establishes permission for this flow.

## Identity, consent, and permissions

### Check 1: identity sign-in

**Confirmed:** The Help Center identity contract releases name, email, and an optional profile picture to supported external applications. Identity sign-in can finish without approving plan usage. Identity sign-in alone does not authorize access to conversations, memory, files, or other product capabilities. The website guide describes an application-specific registered client, state/PKCE/nonce, verified ID-token claims, and an application session. It says an identity-only client must not require OpenAI access or refresh tokens.

**Observed / Provisional:** Hosted Relmio supplies no client ID, scope, issuer, or redirect override to `SignInWithChatGPT` (`web/app/components/ChatConsole.tsx:446-461`). Installed `@openai-oauth/react` is third-party version 2.0.0 (`web/node_modules/@openai-oauth/react/package.json:1-3,49-67`). Its defaults use a fixed client ID, `openid profile email offline_access`, `https://auth.openai.com/oauth/authorize`, `codex_cli_simplified_flow=true`, and a `http://localhost:1455/auth/callback` extension handoff (`web/node_modules/@openai-oauth/core/dist/runtime.js:6-10,179-205`; `web/node_modules/@openai-oauth/web/dist/index.js:8-16,459-504`). The session requires an access token and account ID and can retain ID and refresh tokens. That is not identity-only sign-in.

**Provisional:** The dependency validates callback state, but its JWT helper decodes claims without verifying the signature. The inspected flow does not perform the documented issuer/audience/nonce/signature checks or retain and check granted plan-usage scopes (`web/node_modules/@openai-oauth/core/dist/runtime.js:60-137`; `web/node_modules/@openai-oauth/web/dist/index.js:323-347,505-549`). The nonce embedded in the extension's encoded state is not an OIDC nonce validated against an ID token.

**Observed:** The local n8n wizard starts official Codex CLI login and later reads/copies its complete credential JSON (`src/services/oauth.js:19,258-292,172-198`). Its disclosure correctly says it is not identity-only. The separate managed Codex dashboard uses an App Server `account/login/start` request with `type: chatgptDeviceCode`, not the hosted extension (`src/services/codex-login.js:158-168,203-234`; `src/ui/local.js:5277-5294`).

**Open:** No evidence establishes that Relmio's hosted application is an approved participating identity client, that this fixed-client extension flow is authorized for Relmio, or that the displayed account claims were provider-validated. A stored-session `Connected` badge is not that evidence: it is driven by dependency state, including reading a saved session (`web/app/components/ChatConsole.tsx:403-408`; `web/node_modules/@openai-oauth/react/dist/useSignInWithChatGPT.js:63-73`).

### Check 2: separately approved permissions and ChatGPT plan usage

**Confirmed:** The official open-source flow requests identity scopes `openid profile email` separately from plan-usage scopes `offline_access resource.invoke chatgpt.tokens.use.direct`. Before inference it checks the returned grant for `chatgpt.tokens.use.direct`. Initial registration uses `dynamic_agent_client`, the app's actual name, and `ext_agent_host_id`, then saves the issued client ID. OAuth registration and a deployment checkbox serve different purposes.

**Observed / Provisional:** Hosted Relmio uses only the dependency's default `openid profile email offline_access` request. It does not supply `resource.invoke`, `chatgpt.tokens.use.direct`, the documented resource, an application registration, or a host ID, and does not check the returned plan-usage grant before forwarding requests (`web/app/components/ChatConsole.tsx:446-461`; `web/node_modules/@openai-oauth/core/dist/runtime.js:179-235`; `web/app/api/chat/route.ts:169-191`).

**Observed:** The host Codex invocation passes no explicit OAuth scope argument. Relmio's validation checks JSON shape, `auth_mode`, and nonempty access, ID, and refresh-token fields, not their issuer, granted scopes, or authorization for a separate bridge (`src/services/oauth.js:172-198,263-272`). Its actual CLI-requested/granted scopes remain **Open**; the third-party browser default must not be substituted for them.

**Confirmed / Observed:** The SIWC plan-usage documentation requires the public Responses endpoint and expressly excludes `backend-api`. The hosted route's dependency defaults to `https://chatgpt.com/backend-api/codex`; the n8n sidecar uses the same package family and backend (`web/node_modules/@openai-oauth/core/dist/runtime.js:6,246-266,573-585`; `node_modules/@openai-oauth/core/dist/runtime.js:6,246`; `src/gateway/openai-oauth-sidecar.mjs:183-184`). Neither flow matches that documented transport.

**Confirmed / Observed:** SIWC Terms require requests from a local runtime or a remote runtime controlled only by the user. They require supported sign-in, prohibit general-purpose access for unrelated tools, and require a privacy notice before processing. Accounts and sessions explicitly says to keep tokens out of browser storage. Hosted Relmio persists tokens in IndexedDB and runs provider requests from its hosted Node route. Request-scoped credentials do not resolve these runtime, browser-storage, registration, or grant mismatches.

**Observed:** VPS approval names the adopted SSH recipient and authorizes a credential upload plus sidecar changes. Local approval authorizes the private-volume copy. The code preserves the distinction from provider consent (`src/ui/app.js:1124-1134,1163-1169,1189-1193`; `src/ui/local.js:3230-3232`; `src/ui/ssh-form.js:37-93`). This is useful deployment consent, not a ChatGPT plan-usage grant.

**Open:** The exact applicable agreement depends on the account, region, and any separate written agreement. The SIWC Terms' persistent-storage wording says local/user-controlled, not remote or managed; the developer sessions and self-hosted-VM guides also describe protected self-hosted storage and credential transfer. That tension needs clarification for a proposed compliant VM implementation. It does not establish approval for copying a Codex credential into a general-purpose n8n-compatible bridge. Likewise, the Terms' connected-application-only restriction needs assessment for Relmio's advertised use across other tools.

The ROW and European consumer Terms, Services Agreement, Service Terms, and Usage Policies remain relevant. Their credential-sharing, unauthorized extraction, and anti-circumvention restrictions cannot be waived by a Relmio checkbox or successful login. This report identifies concrete differences from the published flow without issuing a blanket legal compliance or violation determination.

## Model, image, audio, and video boundaries

### Check 3: capability is independent of identity and permission

**Observed:** Hosted chat sends the current trimmed prompt, fixed instructions, model `gpt-5.6-luna`, low reasoning effort, and streaming text options. It supplies no tools and implements no tool execution, file access, command execution, or browsing handler (`web/app/api/chat/route.ts:13-14,169-191`). The browser retains up to twelve turns for display, but sends only the new prompt; previous exchanges are not model context (`web/app/components/ChatConsole.tsx:39,121-129,251-268`).

**Confirmed:** Current Codex model documentation says GPT-5.6 Luna remains available during rollout, while availability still depends on sign-in method, client, plan, rollout, and workspace controls. Naming it in a request or showing a badge does not establish entitlement. The official SIWC guide calls for an account-specific model catalog and completed inference. Hosted Relmio's fixed model and a stored-session badge prove neither.

**Observed / Provisional:** The hosted route disables response-state caching; the dependency normalizes requests to `store:false`, streams them, and may fetch model metadata before inference (`web/app/api/chat/route.ts:177`; `web/node_modules/@openai-oauth/core/dist/runtime.js:389-445,573-580`). The route distinguishes `response.completed` from failure/interruption and requires some text before reporting completion (`web/app/api/chat/route.ts:225-250`). These are source-level controls, not evidence of a successful request.

**Observed / Provisional:** The n8n sidecar exposes image compatibility handlers and appends Flare/Sunburst IDs to successful model lists (`src/gateway/openai-oauth-sidecar.mjs:6-11,80-87`; `node_modules/openai-oauth/dist/chunk-INHW7GRB.js:804-815`). This is implementation support, not OpenAI entitlement or permission. The official Platform image guide documents image generation/editing under its own API conditions. The current SIWC preview limitations explicitly mark image-generation tools unsupported. The wizard's statement that the bridge supports GPT Image must therefore remain clearly qualified as unofficial compatibility, not support through the documented SIWC plan-usage contract (`src/ui/index.html:224`).

**Observed / Confirmed:** The sidecar rejects audio routes with HTTP 501, including speech, transcription, and translation (`src/gateway/openai-oauth-sidecar.mjs:20-25,109-116`). Hosted chat has no TTS route. The official speech guide describes the separate Audio API and requires AI-voice disclosure. ChatGPT Voice Output also has separate Service Terms. Identity sign-in, plan-usage consent, a text response, or reconnecting cannot establish TTS availability.

**Observed / Confirmed:** The previous video mismatch remains: the backend recommends a separate Platform video connection (`src/gateway/openai-oauth-sidecar.mjs:41-45`), while the official deprecation notice records shutdown on 2026-09-24 with no replacement. The current wizard correctly discloses that shutdown (`src/ui/index.html:224`). This is an existing discrepancy, not a new capability.

**Open:** No account-specific text/image entitlement, completed hosted inference, n8n workflow, TTS, or deployed dependency behavior was tested.

## Disclosure mismatches and required qualifications

2. **“Credentials only with your request” is incomplete.** **Observed / Provisional:** The inference access token is request-bound on the hosted server, but browser code also sends exchange and refresh traffic directly to OpenAI.
